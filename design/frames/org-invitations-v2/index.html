Org invitations v2 — Approval Frames

Inviting people into an organization, done properly: choose who (an existing account-holder or an external person), how to reach them (email or WhatsApp), their role and their member type (employee or customer); a brand-new invitee resolves the link, signs up (incl. Google / Facebook) and is auto-bound to the org; and the root owner invites external customers directly. These frames freeze the flows, screens, states and build inventory before any UI is written. Rendered in the fuse-seam design system (tokens only). No identity-vendor name appears — the browser only ever sees app.fuzefront.com and, for social sign-up, accounts.google.com / facebook.com.

Sign up & bind

Create account (Google / Facebook / email, locked to the invited address) → POST /invitations/accept auto-binds → confirms org + role + member type.
Flow 3 · Root customer invite — RootCustomerInviteFlow · route /root/customers
Frame (e) · route /root/customers

Root customer invite

Root owner invites an external person (Gmail / WhatsApp) as a customer; member type fixed, role defaults to Viewer. POST /invitations.
Shared · all flows

States & fail-closed

Loading / empty / error, channel & validation variants, and the fail-closed contract: 410 expired-revoked, 403 mismatch, 409 already-accepted, 409 last-owner, 403 forbidden.

Contract deltas

Invitations have no OpenAPI contract today — v1 is un-contracted Express (backend/src/routes/invitations.ts, organizations.ts). This approval commissions contract-designer to freeze the following in packages/security/openapi.yaml → @fuzefront/security-client:
  • POST /v1/security/tenants/{tenantId}/invitations — create (InvitationCreate → 201 Invitation).
  • GET /v1/security/tenants/{tenantId}/invitations — list pending (InvitationPage, cursor).
  • POST /v1/security/tenants/{tenantId}/invitations/{invitationId}/resend — resend (202; rate-limited).
  • DELETE /v1/security/tenants/{tenantId}/invitations/{invitationId} — revoke (204, idempotent).
  • GET /v1/security/invitations/resolve?token= — public resolve (InvitationPreview; 410 expired/revoked, 409 already-accepted).
  • POST /v1/security/invitations/accept — accept + bind ({token} → 200 Membership; 403 IDENTITY_MISMATCH, 410 expired/revoked, 409 already-accepted).
  • NEW fields: Invitation.channel (email | whatsapp), Invitation.memberType (employee | customer) — member_type is net-new (today the distinction is structural, not a field).
  • NEW delivery: WhatsApp channel (Twilio WhatsApp sender) alongside email (ZeptoMail / services/email-service org-invite template) — WhatsApp is net-new.
  • NEW events: identity.invitation.created / accepted / revoked (Kafka Zod in shared/); accept also emits the existing identity.membership.added.
  • 409 LAST_OWNER invariant on ownership-affecting actions (extends authz-admin's LAST_ADMIN to the owner tier).
