Frame (b) · route /settings/access

Change role

Promote or demote a member within the fixed role enum. Three variants: the ordinary change, and the two refusals that keep an organization governable — it can never be left with no admin, and never with no owner.

(b1) Ordinary change

Change role — rhea@northwind.example

(b2) Last admin — refused (409)

Change role — grace@northwind.example

Northwind needs at least one admin

Grace is the only admin. Promote someone else to admin first, then change Grace's role.
(b3) Last owner — refused (409)

Change role — ada@northwind.example

Northwind needs at least one owner

Ada is the only owner. An owner can only step down once another owner exists — transfer ownership first by promoting someone to owner, then change Ada's role.

Contract. PUT /v1/security/tenants/{tenantId}/members/{userId}/roles (RoleAssignment → 200 Member). The Security service applies the assignment and reflects it into Permit (role-grant sync) in the same owned write — the browser never calls Permit and never infers authorization from client state.

⚠ Two refusals are commissioned by this frame — neither exists in the contract today. (b2) a 409 LAST_ADMIN when the change would leave the org with zero admins, and (b3) a 409 LAST_OWNER when it would leave the org with zero owners. The last-owner invariant is the same one org-invitations-v2 commissions on ownership-affecting actions. Each pairs a server refusal with a client pre-check that disables the offending options. The disabled control is an affordance, not the enforcement — the server must refuse independently, because a client-side guard is not a guard.

⚠ Role replacement is non-atomic today. The provider implements "replace" as remove-then-re-add, so a partial failure can leave a member with no role. Until it is atomic, a failed save must re-fetch and show the member's true current role — never assume the prior value held. A 403 on save (caller lost the manage permission) is shown in place per frame (e), never a sign-in redirect.
