Read-only (non-admin)

A member or viewer can open Access & Roles and see who is in the organization — but holds no permission to change roles or remove anyone. The management affordances are absent, not merely disabled: the UI never renders a control the caller cannot use, and the service refuses the write regardless.

Contract. Same read as frame (a): GET /v1/security/tenants/{tenantId}/members succeeds for any member of the org. What differs is derived from the caller's Permit decision for organization:manage-members on this org: when it is denied, the Actions column, the per-row Change role / Remove buttons, and the Invite action are not rendered at all — there is no disabled-but-present management control. The caller's own row is tagged You.

Why absent, not disabled. A member/viewer legitimately has this page (membership grants the read); rendering greyed-out management controls would mis-state that they could act if something changed, and invite probing. Absence is the honest representation. This is distinct from frame (e)'s 403, which is the fail-closed response when a write is attempted anyway (e.g. the caller lost the permission between render and click) — defense in depth: the UI hides, the server still refuses.
