States

Every state a consumer must render is contract, not decoration. Loading, the single-member org, a load failure, an authorization denial on an attempted action, and the non-member state — with the one rule most often got wrong: an authorization denial must never become a sign-in prompt.

(e5) Not a member — but root is now MEMBER, never GUEST

Members

You're not a member of this organization

You can see it exists, but you hold no membership here. Ask an owner to invite you. This is an authorization state shown in place — never a sign-in redirect.

Reconciliation: this non-member state no longer applies to the root FuzeFront org. Signup now writes a real organization_memberships(role='member') row for root, so the root org resolves to user_role='member' and shows a Member badge — the #529 root GUEST state is retired. It still applies to ordinary orgs you have not joined.

Contract. Loading covers the in-flight GET /v1/security/tenants/{tenantId}/members with aria-busy. Empty is a real, common state — a brand-new org has exactly one member (its creator, the owner). Error covers a non-2xx list response with data-action="retry".

⚠ (e4) and (e5) are the rule this frame exists to enforce. A 403 is an authorization denial, NOT an authentication failure. The caller is signed in and their token is valid; they simply lack permission. (e4) is the fail-closed response when a write is attempted without organization:manage-members (e.g. the permission was revoked between render and click) — the denial is shown in place on the dialog. (e5) is the caller who isn't a member of the org at all. Both render in place and never redirect to sign-in. Only a 401 (no/expired session) re-authenticates. Conflating the two — bouncing a permission-denied user to a login page they'll sail straight back through — is the exact failure these states are contract for.
