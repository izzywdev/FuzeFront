Design-first gate · UX approval · SL9 · contract 4.1.0 · design-record task 13

Selection Lists — shared & common lists, copy-on-write fork

Twelve navigable frames for what a member sees when their organization reads lists it doesn't own: the common-list badge and read-only detail, the “Fork to edit” path from a 409 fork_required, the fork confirmation and every answer it can get, the fork's provenance and “behind source” indicator, the owner's visibility control, and the picker resolving the effective list by key. Every state is contract — loading, empty, error, the fail-closed refusals, and the flag-OFF absence. Built in the fuse-seam design system (tokens only). Requirement: docs/planning/selection-lists-shared-and-fork.md.

ℹ

Approval is per flow — five flows, approved independently

Approving one flow unblocks its implementation (its implementation.paths below) while the others iterate. Each flow's component directory is claimed by that flow alone, so approving one never unlocks a sibling's components; only the shared infrastructure in shared-lists/core/** (types, api, hooks, provider — no rendering components) unlocks with any approval. Flow 3 renders an honest fallback today and carries a named contract dependency (SelectionList.revision); it does not hold any sibling back.

Flow 1 · Shared read — browse, badge, read-only detail

● Awaiting approval
SelectionListManagementFlow (extended) → /settings/selection-lists · any member

A member reads and picks from lists the organization is given without owning them. Common lists are grouped and badged; a fork hides the common list with the same key unless a visibility filter is set; a list read only through visibility is read-only — no mutation affordances at all.

Frame 1a

List index with common lists

“Include common lists” switch, source groups, shadowing note, visibility filter (shadowing off). Loading, two empties, error, flag OFF.
Frame 1b

Common list — read-only detail

Common badge, read-only notice, no edit controls, no Access tab, the one action: Fork to edit.
Frame 1c

Read-only detail — states

Organization list (no fork), “your organization uses its own version”, read-only translations, loading / empty / error / 404, editable-unknown, flag OFF.
Frame 1d

RTL + 375 px — list detail

English, Hebrew and Arabic at phone width. Logical layout, LTR islands for keys and codes.

Flow 2 · Fork to edit

● Awaiting approval
ForkListFlow → /settings/selection-lists/:listId (dialog; no new route) · members who can create lists

A refused change to a common list becomes a way forward; the fork is always an explicit choice with a visibility (organization or private draft), keeps the key, and replaces the common list for the organization. Every answer — 201, 200, the three 409s, quota, the 5,000-value cap, 403, 404, network — has its own state.

Frame 2a

409 fork_required vs 403

The typed change is kept; Fork CTA only with reason: fork_required; 403 explains, no CTA; access ops always 403.
Frame 2b

Fork confirmation

What is copied, same key, replaces the common list, visibility org | private, no-sync note, optional quota preview, submitting.
Frame 2c

Fork results

201 created · 200 existing (active / archived → restore) · fork_exists · fork_not_applicable · key taken · quota · 5,000 cap · 403 · 404 · network.
Frame 2d

RTL + 375 px — fork dialog

The dialog as a bottom sheet in English, Hebrew and Arabic.

Flow 3 · Your fork — provenance & behind source

● Awaiting approval
ForkProvenancePanel → /settings/selection-lists/:listId · fork owners and editors

Where the fork came from, which version it copied, and whether the common list has moved on — informational only, no merge. Revert to common = archive the fork — offered only while an active common list exists; otherwise “Archive fork…” states that forms will have no list.

Frame 3a

Provenance, behind source, revert

Behind / up to date / checking / source archived / source gone / check failed / comparison unavailable; archive-to-revert gated on an active source, archive with the no-list consequence, 403.

Flow 4 · Visibility control

● Awaiting approval
VisibilityControl in SelectionListAccessFlow → /settings/selection-lists/:listId/access · list owners; platform operators

Owners switch private ↔ organization with the consequence spelled out. Publishing as a common list exists only for platform operators in the platform organization, behind a typed confirmation; a common list is locked (visibility_locked).

Frame 4a

Visibility control

Private ↔ organization, saving / saved / 403, read-only for non-owners, loading / error, platform publish, locked, flag OFF.

Flow 5 · Picker — the effective list

● Awaiting approval
SelectionListPicker (extended) → /embed/selection-list-picker (harness) · embedded in consuming forms

Unchanged for the host form, except that a key now means the effective list: the organization's fork if it has one, else the common list. Stored common ids render the fork's label through the resolve redirect, with no visible change.

Frame 5a

Effective list by key

Org with a fork vs one without, private and archived forks, loading / error / no list / flag OFF.
Frame 5b

Stored values across a fork

effective_item_id redirect, every resolve outcome, resolving and resolve-failed.
