Stored values keep rendering across a fork

A record saved last month holds a common item id. Acme has since forked the list.

ℹ

Resolve follows the fork; the picker shows the fork's answer

Forked items get new ids. POST /v1/resolve resolves common ids from every organization and, when the caller's organization holds an organization-visible, active fork with an item whose origin_item_id is that id, returns the fork item's label and names it in effective_item_id. The picker renders that label and selects the matching fork option. One request, as before.

The picker's value is not rewritten: the host gave it the stored id and gets the same id back unless the user picks something else (the picker's contract with its host is unchanged). Both ids keep resolving, so that is always correct. A host that wants to migrate stored values passes onEffectiveValue(stored, effective); the picker calls it once per redirected id after a successful resolve, and the host may write the effective id on its own next save — lazily, as the contract intends. If the user picks a value, the picker emits that option's (fork) id, as for any pick.

Every resolve outcome a stored value can have

Each id renders independently. A batch with a mix of outcomes (some redirected, some missing) is a normal response, not a partial failure.
