Mobile bottom navigation · Approval Frames

375px (phone / Android TWA viewport) frames for the host shell's primary mobile navigation. docs/design-system/portal-ux.md §5 records a real product gap: the design system's mobile guideline specifies a BottomNav below md (≤768px) and the BottomNav primitive exists in @fuzefront/design-system, but it is not wired into the host shell — the shell is drawer-only today, so a phone user has no persistent, thumb-reach navigation. These frames freeze how the bottom nav mounts in the shell, how it coexists with the existing slide-in drawer, and the loading / empty / error / safe-area states before any shell code is written. Built in the fuse-seam design system (tokens only).

Shell chrome present on every authenticated route. Implemented by mobile-frontend-engineer (responsive shell chrome), not in a federated remote. Reuses the existing drawer (SidePanel / .sidebar-scrim in Layout.tsx) rather than adding a second overlay.

Design decisions frozen here

  • 3 primary tabs + More = 4 slots. The DS BottomNav renders max 4 items. The portal has more destinations than fit, so the bar carries the three highest-frequency phone destinations — Home (/dashboard), Apps (/applications), Orgs (/organizations) — and a fourth More tab that opens the existing drawer for the long tail. Derived from SidePanel.tsx's portal section.
  • More reuses the drawer, it does not add a new overlay. Tapping More calls the same toggleSidebar that the top-bar hamburger already calls — one drawer, two entry points, so there is never a bottom-sheet-vs-drawer split to maintain.
  • Nav never blocks on data. The bar renders its static portal destinations immediately; only the app-registry-derived long tail (inside the drawer) has loading/empty/error. Navigation is fail-open — you can always reach Home/Orgs/More even when the registry call fails.
  • Active state is route-derived via aria-current="page", mapped from the router pathname; a federated app route (/app/<slug>) lights the Apps tab.
  • ≥768px is unchanged. At md and up the bottom nav is hidden and the persistent SidePanel returns — these frames specify the phone (xs/sm) treatment only.

Open questions for approval

  • Is Home / Apps / Orgs / More the right four for the bar, or should Billing or Connectors take a primary slot over Orgs? (All others live under More.)
  • When a federated app is active (/app/<slug>), should the bar switch to the app's injected nav, or always stay portal-level with Apps highlighted? These frames assume stay portal-level.
  • Should the bar hide on scroll-down to maximise content height, or stay pinned? Frames assume stay pinned (simplest, most predictable for thumb reach).
