Change history — who turned this off

Append-only. Every set, unset, lock and unlock with its actor, scope, reason and time. Revert is not a delete — it replays an earlier value as a new change, so the revert is itself in the history.

Revert appends, it never rewinds. Entry #4 is a set that happens to carry #2's value, labelled as a revert. Nothing was removed from the log to make it. A history that could be shortened by a UI action is not an audit trail — and "Revert to this" on an unset row (#2) replays the unset, restoring inheritance rather than pinning the value it resolved to at the time.

A · Revert confirmation — states what will actually happen

The dialog shows the current value, the target value, and that a new entry will be written. It carries a reason field, because an unexplained revert is the change people most want explained later.

Revert notifications.digest.frequency to weekly? Current value is daily. This writes a new change setting it back to weekly at org Acme Corp — entry #4 stays in the history, and this revert is added as entry #6. Consumers pick it up on their next read; requiresRestart settings need a restart.

B · A secret key's history — redacted, both sides

The trail records that it changed, never what it was — an audit log holding secret values is a secret store with worse access control. Neither the old nor the new value appears, and "Revert to this" is absent, not disabled: there is no stored plaintext to revert to. Reveals are themselves audited entries.

Anticipated contract (FF-EPIC-18-S2 / S3). Append-only config_value_history written in the same transaction as the value change, so a change can never exist without its audit row. The read and revert surfaces are not in the frozen services/config-service/openapi.yaml today — these frames commission them, and revert is modelled as a replayed set/unset through PUT /v1/config, never as a delete.
