MFA step-up & contact verification — mobile (375px) · Approval Frames

375px (Android TWA viewport) frames for the provider-neutral Security API step-up and contact-verification UX requested in issue #251: choose a factor, enter a one-time code, confirm a phone number, and a combined mobile security-status view. These land in this repo (not an external canvas link) so they can be diffed, schema/DS-conformance checked, and stamped per the design-first gate. Built in the fuse-seam design system (tokens only). No provider name appears anywhere in the UI.

Reached from sign-in (/login/mfa) and from the Account security surface (/account/security, /account/security/verify/phone).

Reconciliation with already-in-repo flows (not greenfield)

  • vs. mfa-management/05-step-up-challenge.html (flow mfa-step-up, unapproved) — same route /login/mfa, same OtpInput/FactorPicker primitives. Frames 01–02 here are the missing 375px treatment + missing loading/empty/generic-error states for that same flow, not a second, divergent step-up design.
  • vs. auth-experience/04-verify-landing.html (flow verify-email, approved) — this is a shipped link-click pattern for email. Frame 03 scopes OTP code-entry to phone only (which has no existing frame) and leaves email on its approved pattern rather than silently swapping a link for a code.
  • vs. account-security/01-hub.html + 02-states.html (flow account-security, approved) — frame 04 is an additive mobile combined view, reusing the hub's chip/badge language; it does not duplicate or re-derive the hub's hasPassword: null guard.

Open for owner ruling

  • Should email verification also move to OTP code-entry for consistency with phone? Assumed no (stay link-click) pending a ruling.
  • Should frame 04 become the TWA's canonical security entry point, or stay secondary to the desktop hub? Assumed secondary/additive pending a ruling.
