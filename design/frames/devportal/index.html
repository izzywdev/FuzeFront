Design-first gate · UX approval · frames-only PR

developers.fuzefront.com — Approval Frames

Nine navigable frames covering the five flows of the new developer portal: a standalone app at developers.fuzefront.com (not a Module-Federation remote — it must be reachable pre-shell, at sign-in, on its own subdomain), structurally modeled on fuzefront-website/frontend/ and sibling to it at repo root. Plan of record: docs/planning/developers-portal.md §4.1 and §7. Built in fuse-seam tokens only. Approving a flow approves its slice of the build inventory below, so the implementation cannot quietly invent a different component or package layout.

1 · Home — flow home · route /

What the portal is, quick links, the sign-in CTA — and, once signed in, the personalized recent-specs and sandbox-activity panels with their empty first-sign-in variants.

Frame 01 · anonymous

Home — signed out

Hero, quick links (Playground shown locked, not hidden), the providesTo product directory, and the sandbox-safety promise stated up front.
Frame 02 · authenticated

Home — signed in

Quota strip, your recent specs, your sandbox activity — plus both panels' empty state for a developer's very first sign-in.

2 · Catalog — flow catalog · route /catalog

Browse product → service → spec, search and filter, with every state the harvest can produce.

Frame 03 · populated

Catalog

TreeNav rail, search + product/tag/sandbox-mode filters, result cards carrying version, operation count, harvest age and sandbox mode (mock vs sandbox).
Frame 04 · states

Catalog states

Loading skeletons · empty (nothing harvested yet) · filtered-empty · error (harvest failed, degrading to a badged stale catalog) · 403 not-a-Developer.

3 · Spec viewer — flow spec-viewer · route /catalog/:product/:service

Our aggregated overview wrapped around an OSS OpenAPI render (Stoplight Elements / Swagger UI — the plan's §3 spike decides which), themed with fuse-seam tokens.

Frame 05 · populated

Spec viewer

Three panes — operations by tag, overview + selected operation (params, request/response schemas, examples, Try it), and copy-paste code samples.
Frame 06 · states

Spec viewer states

Loading · spec-fetch failed (502) · invalid spec (validator output shown, Try-it disabled, source repo named) · 404 not found · stale-spec badge.

4 · Playground — flow playground · route /playground

The "Try it" panel. This is where a wrong state is a security incident, so the fail-closed cases get a frame of their own.

Frame 07 · populated

Playground

Request builder (target selector, params, non-editable auth header, body), response panel, quota meter, and the permanent “this never touches production” notice.
Frame 08 · fail-closed

Playground states

Sending · request-invalid (blocked locally, no quota spent) · 429 quota exceeded · sandbox target unavailable with an explicit no-production-fallback statement · no-sandbox · 403 · proxy 5xx · and target 4xx rendered as data, not as a portal error.

5 · My access — flow my-access · route /access

What the developer holds, and — just as important — what the Developer role does not grant.

Frame 09 · membership · quota · keys

My access

Root-org developer membership with an explicit grants/does-not-grant split, sandbox quota with per-target breakdown, sandbox keys with reveal-once and revoke — plus provisioning, denied (403), empty-keys, error and revoke-confirm states.
