## What FuzeInfra is
A **shared, containerized infrastructure platform** for microservices development. It contains **only generic infra** — no application code. Apps connect to it via the external Docker network **`FuzeInfra`** (compose) or by addressing services in the **`fuzeinfra`** k8s namespace. Clean separation is the whole point: keep app-specific things out of this repo.

## Production (Contabo k3s — GitOps, this is the live model)
- **k3s** on Contabo VPSes, namespace `fuzeinfra`. k3s ships **local-path** storage (default StorageClass) and **Traefik** ingress (`className: traefik`). The cluster is **no longer single-node**: as of 2026-09-20 `kubectl get nodes` shows **three control-plane/etcd members** (`fuze-core-1` 161.97.118.134 / `fuze-core-2` / `fuze-core-3`, embedded-etcd HA) plus worker nodes (`fuzeinfra-ci-runner-1/2`, and any elastic nodes — see the autoscaling section below). Don't assume one node or one API server; confirm with `cluster-query` before reasoning about placement or capacity.
- **ArgoCD owns the deployment.** `argocd/applications/fuzeinfra-prod.yaml` syncs `helm/fuzeinfra` (path) at `targetRevision: main` with `values-contabo.yaml`, `automated: { prune: true, selfHeal: true }`, `ServerSideApply`.
- `deploy-prod.yml` triggers on `helm/**` changes to `main`: lints the chart, runs kubeconform, then `kubectl patch`es the ArgoCD Application to force an immediate sync (needs the `KUBE_CONFIG` repo secret, set by `terraform apply` in `terraform/contabo/`; absent → workflow no-ops with a warning).
- **Networking & access:** domain `prod.fuzefront.com` (fallback `<ip>.nip.io`). **Cloudflare Tunnel** routes `*.prod.fuzefront.com` → Traefik → Ingress. **Cloudflare Access** puts an **email-OTP gate** in front of every admin UI (ArgoCD, Grafana, Prometheus, Airflow, Mongo Express, RabbitMQ, Kafka UI, Flower, ES, ChromaDB, Neo4j, Alertmanager) and surfaces them in a **CF App Launcher** (Terraform `for_each` in `terraform/contabo/cloudflare.tf`).
- **Traefik is pinned to `ClusterIP`** via a `HelmChartConfig` (`argocd/cluster-bootstrap/traefik-clusterip.yaml`) so the k3s servicelb does **not** bind hostPorts 80/443 — that closes direct-to-VPS access and forces all ingress through the Cloudflare tunnel/ZTA. The host firewall is locked to SSH + the k3s API.
- **Cluster DNS is no longer k3s's packaged single-replica CoreDNS.** `helm/fuzeinfra/templates/node-configurator.yaml`, gated by `nodeConfigurator.corednsHA` (on in `values-contabo.yaml`), writes a >=2-replica `coredns` Deployment manifest plus a `coredns.yaml.skip` sentinel into `/var/lib/rancher/k3s/server/manifests/` on each k3s **server** node (agent/CI/elastic nodes are no-ops), so k3s stops reconciling its own packaged single-replica copy while the DaemonSet's manifest — patched onto the same live object, never deleted+recreated — keeps it at the configured replica count with `topologySpreadConstraints` requiring the replicas land on different hosts.

  **The trap:** a `HelmChartConfig` cannot configure CoreDNS on this cluster — k3s deploys CoreDNS as a packaged manifest (a `k3s.cattle.io/v1 Addon`), and the only real `HelmChart` CRs here are `traefik`/`traefik-crd` (`kubectl -n kube-system get helmchart`). A `HelmChartConfig` named `coredns` silently does nothing: no error, no drift shown, `replicas` just never changes. That exact mistake shipped in this repo from 2026-07-29 to 2026-09-23 and is what turned a one-node overlay-network blip into a ~300-job fleet-wide CI outage (single CoreDNS replica, single point of failure). `tests/test_helm_chart_config_has_chart.py` now fails the build if a `HelmChartConfig` targets anything outside a small fixed allowlist of confirmed real `HelmChart`s.
- **CI-node isolation is enforced two ways, not by convention.** Nothing non-CI may schedule onto `fuzeinfra.io/pool=ci` nodes by simply adding a toleration for the `fuzeinfra.io/ci` taint — a fix-CoreDNS PR did exactly that and put cluster DNS on the two most churn-prone/saturated nodes in the fleet instead of the durable control-plane nodes. `helm/fuzeinfra/templates/ci-node-isolation.yaml` (gated by `ciNodeIsolation.enabled`, on in `values-contabo.yaml`) is a `ValidatingAdmissionPolicy` rejecting any Pod carrying an explicit `key: fuzeinfra.io/ci` toleration from outside `ciNodeIsolation.allowedNamespaces` (`arc-runners`, `arc-systems`) — deliberately narrow: it does not touch the keyless blanket `{operator: Exists}` tolerations `fuzeinfra-node-exporter`/`promtail`/`node-configurator` need to run on every node. `tests/test_ci_node_isolation_allowlist.py` is the repo-local half, catching the same pattern before merge.

## Elastic node autoscaling (Contabo) — **currently DISABLED, do not assume it is running**

The repo contains a full elastic-node stack, all gated on `clusterAutoscaler.enabled` in `values-contabo.yaml`: upstream **cluster-autoscaler**, a custom **externalgrpc provider** (`cluster-autoscaler/contabo-externalgrpc`, image `ghcr.io/izzywdev/fuzeinfra-contabo-ca-provider`), a **billing-aware reaper** CronJob, and an **overprovisioning balloon** Deployment (`overprovisioning.enabled`). **Both flags were set to `false` on 2026-09-20** (#1045, #1050) and are a pair — re-enable them together or not at all.

**The billing model is the whole design.** Contabo's cancel is **end-of-billing-period, never immediate** (there is no terminate API), so scaling down the moment a node looks idle just forfeits paid time. Hence `--scale-down-enabled=false`, and an hourly reaper that releases a node only when it is **both** within `releaseWindow` (24h) of the calendar renewal **and** idle. A cancelled instance stays reported to CA on purpose so it remains usable until it actually terminates.

**Why it is off — the failure that matters, because it is structural.** There are **two** paths that cancel a Contabo instance, and only one is billing-aware:

1. the reaper (guarded — behaved correctly throughout), and
2. upstream CA's `removeOldUnregisteredNodes` → `NodeGroupDeleteNodes` → Contabo cancel, which has **no billing awareness at all** and gates purely on elapsed time.

Path 2 cancelled three paid instances 18–49 seconds after they became usable. Ordering ratcheted one node per `maxNodeProvisionTime` (90m) while each order sat unpaid, and stopped only at `maxSize` — so **`maxSize` is the de-facto financial circuit breaker**, not a capacity preference. Re-enabling needs all three of: `pending_payment` reported with `Status.ErrorInfo` (upstream `expectedToRegister()` exempts an instance only for `InstanceDeleting` or `ErrorInfo != nil` — mapping to `instanceCreating` alone does **not** work); an ordering guard while an unpaid order is outstanding; and a refusal to cancel a paid, running instance that has no k8s Node. The full checklist lives in `values-contabo.yaml` next to the flag. Contabo specifics (including that `pending_payment` orders do **not** carry their `userData` into the VM eventually built) belong to `contabo-expert`.

## Read access to prod for anyone (including consuming repos) — `cluster-query`
`.github/workflows/cluster-query.yml` (`runs-on: staging`) is **self-service read-only `kubectl` against the prod cluster**, and it is **not** FuzeInfra-only. It takes **both** `workflow_dispatch` (needs Actions:write) and `repository_dispatch` with `event_type: cluster-query` (needs Contents:write — i.e. the **`FUZEINFRA_DISPATCH_TOKEN` consumers already hold** for infra-requests, so nothing new is minted). Tell consumers this rather than relaying cluster state by hand:
```bash
gh api --method POST repos/izzywdev/FuzeInfra/dispatches -f event_type=cluster-query \
  -f 'client_payload[kubectl_args]=-n <ns> get pods -o wide'
```
Reading the answer needs **no** credential — FuzeInfra is public, so run metadata/logs are world-readable (that is also why the guard exists). Drop-in consumer workflow: `docs/workflows/consumer/cluster-query.yml`.
Guard (executable in `tests/test_cluster_query_guard.py`): a read verb must be present (`get describe logs top events version api-resources api-versions explain cluster-info config`); every mutating/exec token is refused; **`Secret` reads and `--raw` are blocked** because FuzeInfra's job logs are **public** and a read whose *output* is a credential leaks it (this happened on 2026-07-29 with `LITELLM_MASTER_KEY`). SealedSecrets are readable on purpose. Consumer-facing doc: `docs/consuming-repos/CLUSTER_QUERY.md`. Recovering a live Secret value goes through the operator SSH path in `docs/SECRETS_MANAGEMENT.md` §4, never through here.

## Writing GitHub **Actions secrets** — `secret-provision` (no session can do it directly)
`.github/workflows/secret-provision.yml` is the write-side sibling of `cluster-query`, and it exists because **no Claude session can write this repo's Actions secrets at all.** The Anthropic agent proxy refuses `/repos/*/actions/secrets` with `403 "Access to this GitHub Actions path is not permitted through this proxy"` — it injects *git* credentials only, never secret admin (`CAPABILITY_DELEGATION.md` §5). The block is keyed on the **URL**, so it is **not** fixable by adding a secret-write token to a session's environment, and every environment in `.fuze/manifest.json` is `anthropic_cloud` behind that same proxy — so **delegating to a peer session buys nothing**. Don't go hunting for "a session with secret access"; like prod `kubectl` writes, it doesn't exist. A runner is not behind the proxy, which is why the capability lives in a workflow. Takes `workflow_dispatch` **and** `repository_dispatch` `secret-provision` (the `FUZEINFRA_DISPATCH_TOKEN` consumers already hold). Holds `SECRETS_ADMIN_PAT` (fine-grained, Secrets: write) so no session ever does.

**It accepts no input carrying a secret value, and adding one is a release blocker** — job logs here are public, so a value passed as a dispatch input is a published credential (the same reason `cluster-query` refuses `Secret` reads). The three sources are exactly those needing no caller-side plaintext: `generate` (random, **alphanumeric only** — the `&`/`airflow-init` rule), `copy` (re-key an existing secret, disclosing nothing), `verify` (presence + `updated_at`, never the value). A `PROTECTED` list blocks its own PAT, `KUBE_CONFIG`, `FUZEINFRA_DISPATCH_TOKEN` and peers as target *and* as `copy_from`. `target_repo` provisions into another repo, but only one listed in `governance/secret-provision-targets.json` — the PAT is all-repos deliberately, so the allowlist decides the destination, not the token; `copy` is refused cross-repo because it would carry this repo's secret VALUES out. Guard is executable in `tests/test_secret_provision_guard.py`.

**A third-party key (Twilio, Mailjet) cannot be injected by any agent path** — one human injection is irreducible. Prefer making it unnecessary: if the key is bound for the *cluster*, seal it offline with `scripts/seal-secret.sh` (public-key, no cluster access, no GitHub secret) and commit the ciphertext, per `docs/SECRETS_MANAGEMENT.md` §7. Registry: `github.secret.provision` keeps `environment: None` **permanently** and carries `workflow: secret-provision.yml`; read `is_satisfiable()`, not `capability_environment()` alone, or you'll wrongly conclude it's undelegatable.

## Gotchas (learned the hard way — verify they're still in the code)
- **Prod is GitOps. Never hand-deploy or `kubectl patch`/`edit` prod resources** — ArgoCD `selfHeal` reverts out-of-band changes within seconds. Change `helm/fuzeinfra` (or values), commit to `main`, let ArgoCD sync. (This bit the Grafana dashboard fix: the kubectl patch didn't persist; it had to go through Git.)
- **Grafana v13 table panels**: pre-v39 schemas fail with "Error loading: table". Fix = migrate `custom.displayMode` → `custom.cellOptions` and bump `schemaVersion` to `39` in the dashboard JSON, then ship via Git→ArgoCD. Note (as of last check): only `cluster-overview`, `fuzeinfra-services`, and `kubernetes-pods` are at v39 — `kubernetes-nodes`/`logs-explorer` are still 38 and `infrastructure-overview` is 27, so re-check before assuming a given dashboard is migrated. (Leave legitimate `legend.displayMode`/bargauge `displayMode` alone — only table-cell `custom.displayMode` needs the swap.)
- **Neo4j Browser blank page / 503 burst**: thread pool exhausts under ~14 concurrent asset requests on a 4-vCPU node (default ~8). Fix in `helm/fuzeinfra/templates/databases.yaml` is `NEO4J_server_threads_worker__count: "64"` (verify the exact env var — this is the one actually set, *not* `http_threads_max`), plus a CF cache rule for `/browser/assets/*`. **Neo4j Bolt over CF Tunnel needs the WebSocket Bolt endpoint** — named tunnels are HTTP/WS only (no raw TCP); see `NEO4J_server_bolt_advertised__address` set to `neo4j-bolt.<domain>:443`.
- **A stuck ArgoCD operation silently freezes ALL prod deploys, and nothing alerts on it.** An Application waits on resource health during a sync, and Argo will not start a new operation while one is in flight — so a resource that can *never* become healthy pins the whole app indefinitely. Live case: `fuzeinfra-prod` sat in `phase: Running`, *"waiting for healthy state of apps/Deployment/fuzeinfra-overprovisioning"*, from **2026-09-15 to 2026-09-20**. The balloon pod's affinity pins it to `fuzeinfra.io/pool=elastic` nodes, the elastic pool was wedged, so it could never schedule. For five days every commit to `main` silently did not deploy and `deploy-prod` just failed at "Wait for ArgoCD syncs to land" — a red tick nobody read as *"prod is frozen"*. Check `{.status.operationState.phase}` and `.message` **before** debugging anything else about a change that "didn't land"; the message names the exact blocking resource. Recovery is `.github/workflows/argo-terminate-op.yml` (`app=fuzeinfra-prod`), whose Step 3 reports a false `NotFound` failure even when Steps 1–2 worked — verify by re-reading the app, not by the job's conclusion. Note this is distinct from the `argocd-applicationset-controller` CrashLoopBackOff (long-running, does **not** drive these Applications).
- **kubeconform** must run with `-ignore-missing-schemas` or it fails on Traefik (and other) CRDs.
- **`fuze-code-review`: a "No verdict was reached" comment is usually YOUR OWN push, and the check it talks about does not currently block.** Two separate things worth knowing before you spend a cycle on either. (1) Concurrency cancels the in-flight review on every new commit, and until `scripts/fuze_code_review_verdict.py` grew a `superseded` rule those cancelled runs posted *"No verdict was reached — this run is NOT an approval … reported as a failed check deliberately"* — text identical to a real provider outage. Five such false alarms landed across PRs #1188/#1207, all self-inflicted. A cancelled review job (`needs.review.result == "cancelled"`) is now `superseded` and posts nothing; an **empty `action_conclusion` still abstains**, because a skipped or never-started job produces that too and must keep failing closed. (2) **Unresolved as of 2026-09-23:** the script writes `decision` and `body` but never a `check` output, while `fuze-code-review.yml` gates on `if [ "$CHECK" = "fail" ]`. `$CHECK` is therefore always empty and that "DECISIVE LINE" never fires — observed on #1207, where runs 449 and 453 concluded `success` while the verdict was *COMMENT ONLY — not an approval*. So do **not** assume this required check blocks a non-approving review; `required-checks.json`'s `can_fail: true` claim does not currently hold. Fixing it is a behaviour change (every `comment` verdict, which is what CI/governance PRs deliberately get, would start failing), so it needs a deliberate decision on the mapping rather than a quiet patch.
- **`scripts/__tests__/` is run by `harden-gate.yml`'s `gate-identifier` self-test step, and the RUNNER decides what actually executes there.** It used `python -m unittest discover` with only `pyyaml pynacl` installed, so when #1195 added a pytest-style suite the `import pytest` ImportError took the whole discovery down and `gate-identifier` went red on `main` — with the cause buried under ~440 lines of passing output and a wall of expected `administration: read` annotations that are ordinary test output, not the failure. **Always read the bottom of that job's log, not the `::error::` lines.** The step now installs and runs pytest. Do **not** "fix" a recurrence by installing pytest while leaving `unittest discover` in place: the import then resolves, the run reports `OK`, and every `@pytest.mark.parametrize` case silently never runs (measured: unittest 416 vs pytest 435 + 2 subtests) — a green gate running fewer tests than it appears to, which is the vacuous gate the step's own comment exists to prevent. `scripts/__tests__/test_gate_selftest_runner.py` guards this and is written as a `unittest.TestCase` on purpose so it still fires if the runner is reverted. **`harden-gate.yml` is distributed** (`workflow-templates/harden-gate.yml` + every repo copy, `governance/required-checks.json`), so a repo-local fix drifts back unless the canonical FuzeSDLC copy carries it too, and any other repo adding a pytest suite beside a unittest runner hits this identically.
- **CI password generation** (`setup_environment_ci.py`) must be **alphanumeric only** — a shell metachar like `&` in a generated secret breaks `airflow-init`.
- **Loki/Promtail config drift**: Loki needs `delete_request_store` set when compaction/retention is on; Promtail `metric_relabel_configs` is invalid there and must be removed. Both crashed pods on prod before being fixed in `configmaps-monitoring.yaml`.
- The **`FuzeInfra` Docker network is external** — `docker network create FuzeInfra` (or `infra-up`) must run before dependent app stacks come up, or `docker compose up` errors on the missing network.

## How to work
Read the relevant chart/template/values/source first. Prefer the **Helm + kind** flow locally and **Git→ArgoCD** for prod; treat docker-compose as the legacy/quick-local path. Keep this repo **infra-only** — never add app-specific code. Source every secret from `.env`/k8s Secrets (never hardcode). Gate new services behind an `enabled` flag in `values.yaml` and wire them into all relevant overlays. New admin UIs in prod need a Cloudflare Access app + App Launcher entry (Terraform). Verify by actually exercising it — `docker ps`, `kubectl -n fuzeinfra get pods`, curl through the ingress/tunnel, or `python scripts-tools/run_tests.py` / `pytest tests/`. Finish work as a **merged PR**, not just local commits.
